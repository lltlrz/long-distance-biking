# 骑迹计划产品方案

## 0. 项目概述

项目名称：骑迹计划 - 面向长途骑行者的补给感知与分日路线规划工具

项目定位：面向 2 天及以上长途骑行用户，在地图路线规划基础上加入沿途补给识别、分日行程规划和安全风险提醒，帮助用户从“知道怎么走”升级为“知道每天骑到哪里、哪里能补给、哪段路要谨慎”。

目标岗位相关性：该项目围绕地图产品经理常见能力展开，包括用户场景拆解、路线规划、POI 信息组织、路径策略、风险提示、指标体系与 PRD 输出。

## 1. 明确用户和场景

### 1.1 目标用户

本项目优先服务“长途骑行者”，定义为计划连续骑行 2 天及以上，或单次路线超过 100km 的骑行用户。

| 用户类型 | 特征 | 当前行为 | 核心诉求 |
|---|---|---|---|
| 新手长途骑行者 | 有城市骑行或短途骑行经验，第一次计划 2-5 天骑行 | 依赖地图、攻略、小红书/骑行群经验 | 不知道每天骑多远、哪里适合住宿、沿途是否有补给 |
| 低频骑旅用户 | 假期或周末进行 2-7 天骑行 | 手动查路线、住宿、餐饮、城镇 | 想快速生成可执行行程，减少反复查找成本 |
| 进阶骑行爱好者 | 有多次骑行经验，关注效率、爬升、安全 | 会结合地图、GPX、骑行 App、社群反馈规划 | 想提前识别补给空窗、国道大车、弱网络路段 |

### 1.2 非目标用户

| 用户 | 不作为 MVP 核心原因 |
|---|---|
| 城市 1-10km 通勤骑行者 | 需求更偏效率、红绿灯、停车，和长途骑行的补给/分日规划差异较大 |
| 纯运动训练用户 | 更关注功率、心率、配速和训练计划，属于运动数据产品范畴 |
| 专业骑行赛事用户 | 对赛道、补给站、团队协作要求更专业，MVP 难以覆盖 |

### 1.3 核心使用场景

场景一：出发前规划整条长途路线

用户输入起点、终点和计划天数，希望系统生成总路线、每日行程、推荐停留城市/镇点，并提前标注沿途补给和风险。

场景二：选择每日终点

用户知道总路线，但不知道每天应该停在哪里。系统需要结合里程、住宿、餐饮、城镇服务能力和安全风险推荐每日终点。

场景三：判断沿途补给是否可靠

用户担心途中无水、无饭、无住宿，尤其在山区、国道、乡镇之间骑行时，希望地图提示“未来多少公里补给较少”。

场景四：提前规避高风险路段

用户希望提前知道国道占比、大车风险、隧道/桥梁、山区弱网络、夜骑风险，并根据提醒调整路线或出发时间。

### 1.4 用户旅程

| 阶段 | 用户动作 | 用户问题 | 产品机会 |
|---|---|---|---|
| 产生骑行计划 | 决定从 A 地骑到 B 地 | 这条路线能不能骑？需要几天？ | 提供初步行程生成 |
| 出发前查路线 | 打开地图和攻略反复搜索 | 每天骑到哪里？哪里能住？ | 推荐每日终点 |
| 查补给 | 沿路线搜索便利店、餐馆、旅店 | 中间会不会断补给？ | 补给点图层和补给空窗识别 |
| 查风险 | 看道路等级、经验帖、骑友反馈 | 国道大车多吗？山区有信号吗？ | 安全风险提醒 |
| 执行途中 | 按日行程骑行 | 今天是否要提前停？是否继续骑？ | 行程调整和风险再提醒 |

## 2. 用户调研

### 2.1 调研目标

本次调研不直接证明“产品一定成立”，而是验证三个关键假设：

1. 长途骑行用户的核心痛点不是单纯找路线，而是“路线 + 补给 + 分日 + 安全”的组合规划。
2. 用户愿意接受系统推荐每日终点，但推荐理由必须可解释。
3. 补给空窗和安全风险提示比单纯 POI 展示更有决策价值。

### 2.2 调研对象设计

计划访谈 8-12 名用户，样本结构如下：

| 样本类型 | 人数 | 筛选条件 | 重点关注 |
|---|---:|---|---|
| 有 2 天及以上骑行经验用户 | 4-5 | 最近一年有跨城/环线骑行经历 | 真实规划流程、踩坑经历 |
| 有长途骑行意愿但未出发用户 | 3-4 | 有骑行基础，正在考虑长途骑行 | 决策障碍、新手焦虑 |
| 骑行社群/俱乐部用户 | 2-3 | 参与过多人骑行或路线分享 | 经验型策略、路线判断标准 |

### 2.3 访谈提纲

基础信息：

1. 你平时骑行频率如何？最长一次骑行距离/天数是多少？
2. 你通常用哪些工具规划骑行路线？地图 App、Strava、Komoot、社群攻略、Excel 或其他？
3. 你是否有过 2 天及以上骑行经历？路线大概是什么？

路线规划：

1. 你规划长途骑行时，第一步通常做什么？
2. 你会优先确定总路线，还是先确定每天停靠点？
3. 你每天骑行里程一般如何决定？按体力、天数、住宿点、天气还是路况？
4. 你是否会为了住宿或补给改变每日终点？

补给问题：

1. 你会提前查便利店、餐馆、住宿、城镇、修车点吗？
2. 你最担心哪类补给缺失：水、餐饮、住宿、修车、医疗、公厕？
3. 有没有遇到“地图上有点但实际不可用”或“以为有补给但没有”的情况？
4. 如果系统提示“未来 42km 补给较少”，你是否会改变计划？

安全问题：

1. 你是否会避开国道、省道、隧道、桥梁或大车多的路段？
2. 哪些安全信息对你最有帮助？道路等级、大车、路肩、隧道、夜间照明、弱网络？
3. 你能接受为了安全多绕路吗？可接受范围是多少？
4. 你是否会提前下载离线地图？什么情况下会下载？

产品接受度：

1. 如果地图自动生成每日行程，你最希望看到哪些信息？
2. 系统推荐每日终点时，你希望它解释哪些理由？
3. 你更倾向于按“计划天数”规划，还是按“每日里程范围”规划？
4. 你愿意保存、导出或分享这份骑行计划吗？

### 2.4 问卷补充设计

问卷适合用于扩大样本，验证访谈中出现的高频痛点。

| 问题 | 类型 | 目的 |
|---|---|---|
| 你是否有 2 天及以上骑行经历？ | 单选 | 用户分层 |
| 规划长途骑行最麻烦的环节是什么？ | 多选 | 痛点排序 |
| 你最关注哪些沿途信息？ | 多选 | 补给优先级 |
| 你是否遇到过补给不足？ | 单选 | 频率验证 |
| 每日终点通常如何决定？ | 多选 | 分日策略验证 |
| 你愿意为安全多绕多少距离？ | 单选 | 安全权重判断 |
| 你是否需要系统自动生成每日行程？ | 量表 | 需求强度 |

### 2.5 待验证假设和判断标准

| 假设 | 验证方式 | 成立标准 |
|---|---|---|
| 补给不确定是高频痛点 | 访谈和问卷中被主动提及 | 超过半数用户提及餐饮/水/住宿查找麻烦 |
| 用户需要分日行程规划 | 询问是否手动拆分每日终点 | 超过半数用户有手动拆分行为或明确需求 |
| 风险提示需要可解释 | 对比“安全分”和“具体风险说明” | 多数用户偏好具体路段提醒 |
| 推荐终点需要结合城镇服务 | 询问每日终点决策因素 | 住宿、餐饮、城镇服务进入前三因素 |

### 2.6 调研产出形式

- 用户访谈纪要摘要
- 高频痛点词云或痛点表
- 典型用户语录，需获得授权或匿名处理
- 用户旅程图
- 需求优先级矩阵

## 3. 竞品分析

### 3.1 竞品选择逻辑

本项目竞品分为两类：

1. 通用地图产品：高德地图、百度地图。它们强在国内路线规划、POI、导航和本地生活数据。
2. 骑行/户外路线产品：Strava、Komoot、Ride with GPS。它们强在运动路线、户外规划、骑行数据和路线分享。

### 3.2 竞品对比

| 产品 | 核心能力 | 对长途骑行的帮助 | 局限 | 可借鉴点 |
|---|---|---|---|---|
| 高德地图/百度地图 | 路线规划、地点搜索、导航、POI、本地生活 | 国内 POI 丰富，适合查餐饮、住宿、城镇和导航 | 更偏点到点出行，长途骑行分日规划和补给空窗判断不足 | 底层地图、POI 搜索、路径规划、生活服务数据 |
| Strava | 路线创建、运动记录、热力图、路线发现 | 能参考骑友路线和运动数据 | 更偏运动社区，补给/住宿/分日行程能力弱 | 热门路线、用户运动数据、路线保存与分享 |

### 3.3 竞品结论

现有产品分别解决了部分问题，但没有完整覆盖“长途骑行前的行程决策”。

通用地图强在地点和导航，但对长途骑行的分日、补给空窗、安全风险解释不够聚合。骑行产品强在路线和运动记录，但对国内本地生活 POI、住宿餐饮、城镇服务的结合不足。

因此，本项目的机会不是再做一个骑行 App，而是在地图产品中补齐“长距离骑行规划能力”：

- 让 POI 从“附近有什么”变成“沿途哪里能补给”。
- 让路线从“一条路怎么走”变成“每天骑到哪里”。
- 让风险从“用户自己判断”变成“地图提前解释”。

### 3.4 差异化定位

| 维度 | 传统地图路线 | 骑行运动产品 | 骑迹计划 |
|---|---|---|---|
| 核心目标 | 到达目的地 | 记录/发现/训练路线 | 生成可执行长途骑行计划 |
| 规划单位 | 单次 A-B 路线 | 单条路线或运动记录 | 多日行程 |
| POI 使用方式 | 搜索附近地点 | 路线点或收藏点 | 沿途补给能力判断 |
| 风险表达 | 较少骑行专属解释 | 运动路线信息为主 | 国道、大车、弱网络、补给空窗提醒 |
| 适合人群 | 泛出行用户 | 骑行爱好者 | 长途骑行规划用户 |

## 4. 定义问题和机会点

### 4.1 核心问题一：补给不确定

用户在长途骑行中需要持续判断哪里能吃饭、买水、住宿、修车和休息。普通地图虽然可以搜索 POI，但用户需要沿路线多次手动搜索，且很难判断某段路线是否存在补给空窗。

问题表现：

- 用户需要反复缩放地图查找城镇、餐馆和住宿。
- POI 以点形式存在，无法直接转化为“这段路补给是否足够”。
- 地图上有点不等于真实可用，例如营业时间、距离路线、是否仍营业。
- 山区、乡镇、国道之间容易出现长距离无可靠补给。

机会点：补给感知图层

将沿途 POI 聚合为补给能力判断，并用路段化方式提醒用户：

- 未来 20km 补给充足。
- 未来 35km 仅有 1 个村镇，建议提前补水。
- Day 2 第 68-94km 为补给空窗，建议不要夜间通过。

### 4.2 核心问题二：分日行程难规划

长途骑行用户的真实问题不是“从 A 到 B 有多远”，而是“每天骑到哪里比较合理”。普通地图给出总路线和总耗时，但不会结合天数、体力、住宿点和补给情况自动拆分行程。

问题表现：

- 用户需要自己把总路线拆成 Day 1、Day 2、Day 3。
- 仅按平均里程拆分可能把每日终点落在无住宿或补给薄弱区域。
- 用户难以同时平衡里程、爬升、住宿、餐饮和次日衔接。
- 新手用户不清楚每天骑多少比较合适。

机会点：分日行程规划

系统根据计划天数、每日里程范围和骑行强度推荐每日终点。推荐终点优先选择有住宿、餐饮、城镇服务和较低安全风险的位置。

### 4.3 核心问题三：安全风险前置不足

长途骑行风险常出现在国道、省道、大车、隧道、山区、弱网络、夜骑等场景。用户往往需要依赖经验帖、社群或人工判断，地图没有充分把这些风险转化为骑行决策信息。

问题表现：

- 用户不知道某条国道是否大车较多。
- 隧道、桥梁、连续弯道等路段在地图中不够突出。
- 弱网络区域会影响路线重算、搜索、联系他人和加载地图。
- 夜间继续骑行时，补给不足和道路风险会叠加。

机会点：安全风险解释

不只给安全分，而是提供具体、可操作的风险提醒：

- 第 47-63km 国道路段较长，建议白天通过。
- 第 20-35km 山区弱网络风险，建议提前下载离线地图。
- 第 88km 后补给稀疏，不建议夜间继续骑行。

### 4.4 机会优先级

| 机会点 | 用户价值 | 实现复杂度 | MVP 优先级 |
|---|---|---|---|
| 沿途补给点展示 | 高 | 中 | P0 |
| 补给空窗识别 | 高 | 中 | P0 |
| 分日行程规划 | 高 | 中高 | P0 |
| 每日终点推荐解释 | 高 | 中 | P0 |
| 国道/大车/弱网络提醒 | 中高 | 中高 | P1 |
| 天气联动 | 中 | 中 | P2 |
| 社区反馈补充路况 | 中 | 高 | P2 |
| 组队/分享 | 中 | 中 | P2 |

## 5. 方案设计

### 5.1 产品目标

用户目标：帮助长途骑行者快速生成可执行、可调整、可避险的骑行计划。

产品目标：提升地图在长距离骑行场景中的规划深度，从单次路线导航扩展到多日行程决策。

求职作品集目标：展示对地图产品中路线规划、POI、场景化策略、用户调研和指标设计的理解。

### 5.2 MVP 范围

P0 必须包含：

- 起点、终点、计划天数输入。
- 骑行强度选择：轻松、标准、挑战。
- 总路线生成。
- 每日行程拆分。
- 每日推荐终点。
- 沿途补给点图层。
- 补给空窗提醒。
- 基础安全风险提醒。

P1 可增强：

- 用户自定义每日里程范围。
- 住宿优先、安全优先、少爬升、补给优先偏好。
- 替换每日终点。
- 离线地图下载提醒。
- 路线导出 GPX。

P2 暂不做：

- 社交组队。
- 骑行社区内容。
- 实时大车流量预测。
- 天气深度预测。
- 装备管理。
- 运动训练数据分析。

### 5.3 核心功能一：沿途补给图层

功能说明：路线生成后，系统自动识别路线两侧一定范围内的补给点，并按类型展示。

补给类型：

| 类型 | 示例 | 价值 |
|---|---|---|
| 食物 | 餐馆、小吃店、超市 | 用餐和能量补充 |
| 水和日用品 | 便利店、超市、加油站 | 补水、购买基础物资 |
| 住宿 | 酒店、宾馆、民宿、旅店 | 每日终点选择 |
| 城镇服务 | 城镇、村庄、乡镇中心 | 判断综合服务能力 |
| 医疗 | 医院、卫生院、药店 | 应急保障 |
| 维修 | 自行车店、修车点 | 车辆故障处理 |
| 公共设施 | 公厕、公共服务站 | 中途休整 |

补给展示规则：

| 补给状态 | 判断示例 | 视觉表达 | 用户提示 |
|---|---|---|---|
| 充足 | 未来 20km 内多类补给密集 | 绿色 | 补给充足，可按计划骑行 |
| 一般 | 未来 20-40km 有少量补给 | 黄色 | 建议在下一个城镇补水 |
| 稀疏 | 超过 40km 缺少可靠补给 | 红色 | 前方补给较少，建议提前准备 |

### 5.4 核心功能二：补给空窗识别

功能说明：系统沿路线计算连续无可靠补给的路段，并在总览和每日行程中提示。

识别逻辑：

1. 将路线按距离切分为若干路段。
2. 查询路线缓冲区内 POI 和城镇/村庄点。
3. 判断每个路段是否存在可用补给。
4. 连续无补给超过阈值时标记为空窗。
5. 根据空窗长度、位置、是否接近夜间、是否处于山区等因素给出风险等级。

阈值建议：

| 用户强度 | 补给空窗提醒阈值 |
|---|---:|
| 轻松 | 25km |
| 标准 | 35km |
| 挑战 | 50km |

### 5.5 核心功能三：分日行程规划

功能说明：用户输入起终点和计划天数后，系统自动拆分每日路线，并推荐每日终点。

输入项：

- 起点。
- 终点。
- 计划骑行天数。
- 骑行强度：轻松、标准、挑战。
- 偏好：住宿优先、安全优先、补给优先、少爬升。

输出项：

| 字段 | 说明 |
|---|---|
| 每日路线 | Day N 起点到终点 |
| 每日里程 | 当天预计骑行距离 |
| 预计耗时 | 基于骑行速度和路况估算 |
| 推荐终点 | 城镇、县城、乡镇或住宿点密集区域 |
| 补给风险 | 低、中、高 |
| 安全提醒 | 国道、大车、隧道、弱网络等 |

每日终点推荐策略：

推荐终点不应按平均里程硬切，而应在目标里程范围内选择综合服务能力更强的地点。

评分模型示例：

```text
每日终点得分 = 住宿可达性 40% + 餐饮/便利店密度 25% + 与目标里程匹配度 20% + 安全风险 15%
```

### 5.6 核心功能四：安全风险提醒

功能说明：系统识别骑行风险路段，并在总览页和每日行程页展示。

风险类型：

| 风险 | 判断依据 | 提示方式 |
|---|---|---|
| 国道/省道占比高 | 道路等级和路线长度占比 | 标注高风险路段 |
| 大车风险 | 道路类型、货运通道、用户反馈或平台历史数据 | 建议白天通过 |
| 隧道/桥梁 | 道路结构点 | 提醒开启车灯、注意避让 |
| 连续爬升/山路 | 海拔和坡度数据 | 提醒体力和补给准备 |
| 弱网络风险 | 历史信号数据或山区/偏远区域推断 | 建议提前下载离线地图 |
| 夜骑叠加风险 | 预计到达时间和补给/道路风险叠加 | 建议提前停靠 |

### 5.8 数据与策略依赖

| 数据 | 用途 |
|---|---|
| 路网数据 | 路径规划、道路等级、隧道/桥梁识别 |
| POI 数据 | 餐饮、便利店、住宿、医疗、维修等补给识别 |
| 行政区划/城镇数据 | 判断城镇服务能力和每日终点 |
| 海拔/坡度数据 | 判断爬升和体力消耗 |
| 用户反馈数据 | 补充路段风险和 POI 可用性 |
| 平台历史骑行数据 | 优化预计耗时和推荐终点 |

### 5.9 指标体系

| 指标 | 定义 | 作用 |
|---|---|---|
| 路线生成成功率 | 输入起终点后成功生成长途计划的比例 | 衡量基础可用性 |
| 行程保存率 | 用户保存分日计划的比例 | 衡量方案价值 |
| 推荐终点采纳率 | 用户未修改推荐终点的比例 | 衡量推荐质量 |
| 补给点点击率 | 用户点击补给点的比例 | 衡量补给图层价值 |
| 补给空窗查看率 | 用户查看空窗详情的比例 | 衡量风险提示价值 |
| 安全提醒查看率 | 用户展开安全提醒的比例 | 衡量安全模块价值 |
| 行程调整率 | 用户手动调整天数/终点/偏好的比例 | 发现策略优化空间 |
