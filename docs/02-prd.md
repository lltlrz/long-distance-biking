# 骑迹计划 PRD 规范书

## 1. 文档信息

| 字段 | 内容 |
|---|---|
| 产品名称 | 骑迹计划 |
| 文档类型 | PRD 产品需求文档 |

## 2. 背景与目标

### 2.1 背景

长途骑行用户在出发前通常需要完成路线选择、每日行程拆分、住宿点选择、沿途补给查询和安全风险判断。现有地图产品能够提供路线规划和 POI 搜索，但更偏单次 A-B 导航，用户仍需手动把路线拆成多日计划，并反复查询便利店、餐馆、旅店、城镇村庄等补给信息。

骑行类产品能够提供路线记录、热门路线和运动数据，但对国内本地生活 POI、住宿餐饮和城镇服务能力的结合不足。因此，本项目希望在地图路线规划中增加长途骑行专属能力，帮助用户形成可执行、可调整、可避险的骑行计划。

### 2.2 产品目标

| 类型 | 目标 |
|---|---|
| 用户目标 | 降低长途骑行前路线和行程规划成本，提升补给与安全确定性 |
| 产品目标 | 将地图骑行路线从“单次导航”扩展为“多日行程规划” |
| 业务目标 | 提升地图产品在长距离骑行、户外出行、路线规划场景中的使用深度 |

### 2.3 成功指标

| 指标 | 口径 | 目标方向 |
|---|---|---|
| 路线生成成功率 | 用户提交起终点和计划天数后成功生成计划的比例 | 提升 |
| 行程保存率 | 用户保存生成行程的比例 | 提升 |
| 推荐终点采纳率 | 用户未修改系统推荐终点的比例 | 提升 |
| 补给点点击率 | 用户点击沿途补给点的比例 | 提升 |
| 补给空窗查看率 | 用户查看补给空窗详情的比例 | 提升 |
| 安全提醒查看率 | 用户展开或点击安全提醒的比例 | 提升 |
| 行程二次调整率 | 用户修改天数、强度、终点或偏好的比例 | 合理区间，用于发现策略问题 |

## 3. 用户与场景

### 3.1 目标用户

| 用户类型 | 描述 | 需求重点 |
|---|---|---|
| 新手长途骑行者 | 第一次或低经验进行多日骑行 | 分日规划、补给提醒、安全解释 |
| 低频骑旅用户 | 假期骑行，骑行经验有限 | 快速生成可执行计划，减少查找成本 |
| 进阶骑行爱好者 | 熟悉路线规划，关注效率和风险 | 可解释策略、路线调整、风险识别 |

### 3.2 典型场景

场景一：用户计划从成都骑到乐山，预计 3 天完成，希望系统推荐每天骑到哪里，并查看沿途住宿和补给。

场景二：用户计划环湖骑行，路线中有乡镇和山区，希望提前知道哪段补给少、哪段可能弱网络。

场景三：用户发现 Day 2 里程过长，希望替换推荐终点，让行程更轻松。

### 4.2 约束与假设

1. V1.0 重点是出发前规划，不做实时导航完整闭环。
2. 补给点以地图 POI 数据为基础，但需要承认 POI 可能存在过期、不准确、营业状态未知等问题。
3. 安全风险中的“大车风险”和“弱网络风险”在作品集中可作为策略设计，不声称已有真实生产数据。
4. 每日行程推荐以可解释为优先，不追求复杂算法表达。

## 5. 用户流程

### 5.1 主流程

1. 用户进入长途骑行规划入口。
2. 输入起点和终点。
3. 输入计划骑行天数。
4. 选择骑行强度：轻松、标准、挑战。
5. 选择偏好：住宿优先、安全优先、补给优先、少爬升。
6. 点击“生成骑行计划”。
7. 系统展示总览页：总里程、总天数、每日路线、补给风险、安全风险。
8. 用户进入某一日详情页查看补给点、补给空窗和风险提醒。
9. 用户可替换每日终点或调整强度后重新生成。
10. 用户保存行程。

### 5.2 异常流程

| 场景 | 系统处理 |
|---|---|
| 起点或终点无法识别 | 提示用户重新输入，并给出候选地点 |
| 路线生成失败 | 提示当前路线无法生成，建议调整起终点或出行方式 |
| 计划天数过少 | 提示每日里程过高，并建议增加天数或选择挑战强度 |
| 目标里程范围内无合适住宿点 | 推荐最近可住宿城镇，并说明会增加或减少里程 |
| 补给数据不足 | 提示“该区域补给数据有限，建议提前确认” |
| 弱网络风险路段 | 提示提前下载离线地图 |

## 6. 功能需求

### 6.1 功能一：长途骑行规划入口

#### 6.1.1 功能描述

用户通过入口进入长途骑行规划模式，区别于普通骑行导航。该模式强调多日规划、补给、住宿和安全风险。

#### 6.1.2 输入项

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| 起点 | 地点输入 | 是 | 支持当前位置、POI、城市、地址 |
| 终点 | 地点输入 | 是 | 支持 POI、城市、地址 |
| 计划天数 | 数字输入 | 是 | 最小 2 天，最大建议 14 天，根据平台数据自动计算并填入默认值 |
| 骑行强度 | 单选 | 是 | 轻松、标准、挑战 |
| 偏好 | 多选 | 否 | 住宿优先、安全优先、补给优先、少爬升 |

#### 6.1.3 规则

| 规则编号 | 规则 |
|---|---|
| R1 | 计划天数小于 2 时，引导用户使用普通骑行路线 |
| R2 | 若按计划天数计算的日均里程超过挑战强度上限，提示增加天数 |
| R3 | 偏好未选择时，默认按标准强度 + 住宿优先生成 |

### 6.2 功能二：分日行程生成

#### 6.2.1 功能描述

系统根据总路线、计划天数、骑行强度和偏好拆分每日行程，并推荐每日终点。

#### 6.2.2 骑行强度规则

| 强度 | 建议日里程 | 适合用户 |
|---|:--:|---|
| 轻松 | 50-70km | 新手、休闲骑旅 |
| 标准 | 70-100km | 有一定骑行基础用户 |
| 挑战 | 100-130km | 进阶用户 |

#### 6.2.3 每日终点推荐规则

每日终点应在目标里程范围内优先选择综合服务能力更强的城镇或住宿聚集区。

```text
每日终点得分 = 住宿可达性 40% + 餐饮/便利店密度 25% + 目标里程匹配度 20% + 安全风险 15% 
```

| 因子 | 说明 |
|---|---|
| 住宿可达性 | 推荐终点附近是否有酒店、旅店、民宿等 |
| 餐饮/便利店密度 | 是否满足晚餐、早餐、补水采购需求 |
| 目标里程匹配度 | 与当前强度建议日里程是否接近 |
| 安全风险 | 是否避开高风险路段后结束当日骑行 |
| 次日衔接顺畅度 | 次日是否能继续按合理里程推进 |

#### 6.2.4 输出字段

| 字段 | 说明 |
|---|---|
| Day 编号 | 第几天 |
| 当日起点 | 当天起点 |
| 当日终点 | 推荐终点 |
| 当日里程 | 预计骑行距离 |
| 预计耗时 | 基于速度和路线估算 |
| 推荐理由 | 例如住宿集中、餐饮较多、次日衔接顺畅 |
| 补给风险 | 低、中、高 |
| 安全风险 | 低、中、高 |

### 6.3 功能三：沿途补给点展示

#### 6.3.1 功能描述

在总路线和每日路线中展示沿途补给点，帮助用户理解每段路的服务能力。

#### 6.3.2 补给类型

| 类型 | POI 示例 | 图层默认状态 |
|---|---|---|
| 餐饮 | 餐馆、小吃、快餐 | 默认展示 |
| 水和日用品 | 便利店、超市、加油站 | 默认展示 |
| 住宿 | 酒店、宾馆、民宿、旅店 | 默认展示 |
| 城镇/村庄 | 乡镇、村庄、县城 | 默认展示 |
| 医疗 | 医院、卫生院、药店 | 默认关闭，可手动打开 |
| 维修 | 自行车店、修车点 | 默认关闭，可手动打开 |
| 公厕 | 公共厕所 | 默认关闭，可手动打开 |

#### 6.3.3 展示规则

| 规则编号 | 规则 |
|---|---|
| R1 | 默认展示路线两侧一定范围内的补给点 |
| R2 | POI 过密时按类型聚合展示，避免地图拥挤 |
| R3 | 用户点击补给点后展示名称、距离路线、类型、营业信息和导航入口 |
| R4 | 住宿类 POI 在每日终点附近优先展示 |

### 6.4 功能四：补给空窗识别

#### 6.4.1 功能描述

系统识别连续缺少可靠补给的路段，并在总览页、每日行程页和地图上提示。

#### 6.4.2 判断规则

| 强度 | 补给空窗提醒阈值 |
|---|---:|
| 轻松 | 连续 25km 缺少可靠补给 |
| 标准 | 连续 35km 缺少可靠补给 |
| 挑战 | 连续 50km 缺少可靠补给 |

可靠补给定义：餐饮、便利店、超市、加油站、城镇/村庄中至少存在一种，并且距离路线不超过设定范围。

#### 6.4.3 风险等级

| 等级 | 判断 | 提示 |
|---|---|---|
| 低 | 空窗距离低于阈值 | 不单独打扰，仅在详情中展示 |
| 中 | 空窗距离达到阈值 | 提醒提前补水/用餐 |
| 高 | 空窗距离明显超过阈值，且叠加山区、夜间或安全风险 | 强提醒，并建议调整行程 |

### 6.5 功能五：安全风险提醒

#### 6.5.1 功能描述

识别长途骑行中需要提前关注的风险路段，并给出具体说明和建议。

#### 6.5.2 风险类型

| 风险类型 | 触发依据 | 用户提示 |
|---|---|---|
| 国道/省道占比高 | 当日路线中高级道路占比高 | “该日国道路段较长，建议白天通过” |
| 大车风险 | 道路类型、货运道路、历史反馈 | “该路段可能有较多大车，请注意靠右和避让” |
| 隧道/桥梁 | 路网结构识别 | “前方有隧道/桥梁，请提前开启车灯” |
| 山区/连续爬升 | 海拔和坡度信息 | “该路段爬升较多，建议提前补给” |
| 弱网络风险 | 偏远区域、山区或历史信号信息 | “建议提前下载离线地图” |
| 夜骑叠加风险 | 预计通过时间较晚且叠加补给/道路风险 | “不建议夜间继续通过该路段” |

#### 6.5.3 展示原则

1. 风险提示必须具体到路段，不只给总分。
2. 同一日风险过多时优先展示高风险和可行动建议。
3. 安全分仅作为辅助，核心是解释原因。
4. 不使用恐吓式文案，强调“建议”和“准备”。

### 6.6 功能六：行程调整

#### 6.6.1 功能描述

用户可调整每日终点、计划天数、骑行强度和偏好，系统重新生成计划。

#### 6.6.2 调整项

| 调整项 | 说明 |
|---|---|
| 替换每日终点 | 从候选城镇/住宿点中选择新终点 |
| 调整计划天数 | 增加或减少总天数 |
| 调整骑行强度 | 轻松、标准、挑战之间切换 |
| 调整偏好 | 住宿优先、安全优先、补给优先、少爬升 |

#### 6.6.3 规则

| 规则编号 | 规则 |
|---|---|
| R1 | 用户替换某日终点后，系统自动重算后续每日路线 |
| R2 | 若新终点导致次日里程过高，需提示用户 |
| R3 | 用户调整天数后，系统重新拆分全程 |
| R4 | 用户调整偏好后，保留起终点和天数不变 |

## 7. 页面需求

### 7.1 页面一：路线规划页

页面目标：收集生成长途骑行计划所需的关键输入。

核心组件：

- 起点输入框。
- 终点输入框。
- 计划天数输入器。
- 骑行强度单选。
- 偏好多选。
- 生成计划按钮。

状态说明：

| 状态 | 说明 |
|---|---|
| 默认 | 展示输入项和默认标准强度 |
| 输入中 | 地点输入提供候选地点 |
| 校验失败 | 缺少起点、终点或天数时提示 |
| 生成中 | 展示加载状态 |

### 7.2 页面二：行程总览页

页面目标：让用户快速判断整条路线是否可执行。

核心组件：

- 总路线地图。
- 总里程、总天数、预计总耗时。
- 每日行程卡片。
- 补给风险总览。
- 安全风险总览。
- 保存行程按钮。

每日行程卡片字段：Day 编号、起终点、里程、预计耗时、推荐理由、补给风险、安全风险。

### 7.3 页面三：每日行程详情页

页面目标：展示某一天的可执行路线和风险信息。

核心组件：

- 当日地图路线。
- 当日里程与预计耗时。
- 推荐终点说明。
- 补给点列表。
- 补给空窗提醒。
- 安全风险提醒。
- 替换终点入口。

### 7.4 页面四：补给图层页

页面目标：让用户按类型查看沿途补给点。

核心组件：

- 图层筛选器：餐饮、水和日用品、住宿、城镇、医疗、维修、公厕。
- 地图 POI 标记。
- 补给密度分段条。
- 补给空窗高亮。
- POI 详情弹层。

### 7.5 页面五：行程调整页

页面目标：让用户基于系统推荐进行人工修正。

核心组件：

- 当前每日终点列表。
- 候选终点列表。
- 调整后里程变化。
- 补给风险变化。
- 安全风险变化。
- 确认调整按钮。

## 8. 数据需求

| 数据类型 | 字段示例 | 用途 |
|---|---|---|
| 路网数据 | 道路等级、道路类型、隧道、桥梁 | 路线规划和安全风险识别 |
| POI 数据 | 名称、类型、坐标、营业信息 | 补给点展示 |
| 住宿数据 | 酒店/宾馆/民宿位置和状态 | 每日终点推荐 |
| 城镇数据 | 城镇、村庄、行政区划 | 综合服务能力判断 |
| 海拔坡度数据 | 海拔、爬升、坡度 | 骑行强度和风险判断 |
| 用户反馈 | POI 是否可用、路段是否危险 | 后续优化补给和安全判断 |
| 历史骑行数据 | 骑行速度、路线完成情况 | 预计耗时和强度推荐 |

## 9. 非功能需求

| 类型 | 要求 |
|---|---|
| 性能 | 计划生成应在可接受时间内完成，复杂路线可先返回总览再补充详情 |
| 可解释性 | 推荐终点、补给风险、安全风险都需要展示原因 |
| 易用性 | 新手用户不需要理解复杂骑行术语即可生成计划 |
| 可扩展性 | 后续可接入天气、GPX 导出、社区反馈、骑行导航 |
| 安全性 | 不承诺绝对安全，提示为辅助决策 |

## 11. 验收标准

| 功能 | 验收标准 |
|---|---|
| 起终点和天数输入 | 用户可以输入有效起终点和 2 天及以上计划天数 |
| 分日行程生成 | 系统能生成 Day 1 至 Day N 的起终点、里程和推荐理由 |
| 补给点展示 | 用户能按类型查看沿途补给点 |
| 补给空窗提醒 | 当连续无可靠补给超过阈值时，系统能提示空窗路段 |
| 安全风险提醒 | 系统能展示至少国道/省道、隧道/桥梁、弱网络三类风险 |
| 行程调整 | 用户替换每日终点后，系统能重新计算后续行程 |
| 保存行程 | 用户能保存生成后的计划 |

## 12. 风险与后续迭代

### 12.1 产品风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 长途骑行人群较小 | 面试官可能质疑规模 | 强调该能力可迁移到摩旅、自驾游、徒步、露营等长距离出行 |
| POI 数据准确性不足 | 补给判断可能误导用户 | 增加数据可信度提示和用户反馈入口 |
| 安全风险难以量化 | 容易被质疑数据来源 | 用概念模型表达，区分已有数据和待验证数据 |
| 功能范围过大 | 作品集显得不聚焦 | MVP 聚焦补给、分日、安全三个模块 |

### 12.2 后续迭代方向

1. 接入天气，提示高温、降雨、逆风等骑行风险。
2. 支持 GPX 导入和导出，服务进阶骑行用户。
3. 增加骑友反馈，补充 POI 可用性和路段风险。
4. 增加行程分享，方便多人骑行前协作。
5. 接入实时导航，在骑行中动态提醒补给和风险。
