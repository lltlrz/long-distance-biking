# 骑迹计划 V2 高低保真模型改版设计

## 1. 目标

依据 `docs/面向长途骑行者的补给感知与分日路线规划工具.md`，升级现有低保真模型、Figma 高保真模型和代码 Demo，使三套交付物完整表达 AI 分日规划、补给感知、安全提醒与动态行程调整能力。

本次采用渐进增强方案：保留现有三栏地图工具框架，增加 AI 推荐解释和动态调整闭环，不改成聊天机器人界面。

## 2. 交付与版本隔离

所有改版内容均另存，不覆盖原模型：

- 低保真文档：`docs/05-low-fidelity-prototype-v2.md`
- 高保真说明：`docs/06-figma-high-fidelity-prototype-v2.md`
- 可交互 Demo：`demo-v2/`
- Figma 副本：`骑迹计划 V2 - 高低保真模型`

原有 `docs/05-low-fidelity-prototype.md`、`docs/06-figma-high-fidelity-prototype.md`、`demo/` 和原 Figma 文件保持不变。

## 3. 产品范围

### 3.1 V2 核心能力

1. 根据起终点、计划天数、骑行强度和路线偏好生成分日计划。
2. 解释每日终点的推荐原因，包括里程、爬升、住宿、补给与后续衔接。
3. 在地图和每日详情中展示餐饮、便利店、住宿、城镇、维修等补给点。
4. 识别补给空窗，并展示距离、风险等级和准备建议。
5. 展示国道、省道、隧道、山区、弱网络等基础安全提醒。
6. 接收当前进度、疲劳程度、天气变化和时间限制，生成局部调整建议。
7. 在用户确认前展示调整影响，确认后再应用新计划。

### 3.2 非本次范围

- 实时天气深度联动
- 基于历史数据的个性化骑行能力模型
- GPX 导出
- 社区、组队与多人协同
- 真实地图、POI 或路线服务接入

代码 Demo 使用确定性模拟数据表达产品行为，不暗示已接入实时服务。

## 4. 信息架构

主工作台继续使用三栏结构：

| 区域 | 内容 | 用户任务 |
|---|---|---|
| 左侧规划面板 | 起终点、天数、强度、偏好、生成按钮、途中状态入口 | 输入条件、发起规划或调整 |
| 中间地图画布 | 总路线、分日路段、补给点、补给空窗、城镇标签 | 理解路线与空间风险 |
| 右侧决策面板 | 每日卡片、推荐理由、补给与安全提醒、调整入口 | 判断计划是否可执行 |

动态调整使用抽屉或覆盖面板完成，不离开地图工作台。

主流程为：

`输入规划条件 → AI 生成分日计划 → 查看地图与推荐解释 → 发现补给或安全风险 → 提交途中状态 → 预览调整影响 → 确认重新规划 → 保存`

## 5. 页面与状态设计

### 5.1 规划输入状态

- 起点、终点、计划天数和总里程。
- 轻松、标准、挑战三档骑行强度。
- 住宿优先、补给优先、安全优先、少爬升等偏好。
- 主操作文案为“生成 AI 骑行方案”。
- 点击后展示生成中状态，并在成功或失败后给出明确反馈。

### 5.2 规划结果状态

- 地图居中展示总路线、分日颜色、补给 POI 和补给空窗。
- 每日卡片显示起终点、里程、耗时、爬升、补给状态和安全等级。
- 选中每日卡片后，地图聚焦对应路段，右侧同步显示推荐理由。
- 推荐理由至少解释日均里程匹配、终点服务能力和次日衔接三个维度。

### 5.3 补给与安全状态

- 补给筛选包括餐饮、便利店、住宿、城镇和维修。
- 补给空窗显示具体路段或里程范围、连续距离和建议动作。
- 安全提醒使用可执行文案，如“建议白天通过”或“提前下载离线地图”。
- 数据非实时或可信度不足时，展示更新时间或“信息待确认”。

### 5.4 动态调整状态

- 入口提供体力下降、天气变化、时间不足和进度滞后四类快捷选择。
- 调整抽屉展示当前完成距离、疲劳程度和限制条件。
- AI 输出是否建议调整、新停留点、调整原因及对后续日程的影响。
- 调整影响采用前后对比，至少包含 Day 里程变化、补给空窗变化和风险变化。
- 用户点击“确认重新规划”后才应用结果；取消时原计划保持不变。

### 5.5 保存状态

- 保存成功使用轻量 Toast，不中断当前浏览。
- 保存内容为当前已确认版本，而不是尚未确认的调整预览。

## 6. 视觉规范

- 主色使用深绿和青绿色，用于品牌、主按钮、选中状态与路线。
- 橙色用于需要关注的建议和中风险。
- 红色只用于明确的补给空窗或高风险路段。
- 绿色用于补给充足和安全状态。
- 地图保持最高视觉权重；控制和解释信息采用白色卡片承载。
- AI 内容使用推荐理由卡、影响对比卡和状态标签，不使用聊天气泡。
- 中文信息层级清楚，关键数值和行动建议优先于说明文字。

## 7. 异常处理

| 异常 | 处理方式 |
|---|---|
| 起终点无法识别 | 展示候选地点，保留用户原输入 |
| 天数过少或日均里程过高 | 解释超出强度范围，并建议增加天数或调整强度 |
| 目标范围内无理想住宿点 | 推荐最近可住宿城镇，并说明里程偏差 |
| 路线生成失败 | 保留规划条件，提供修改和重试入口 |
| 动态数据不可用 | 标明更新时间或不可用状态，不输出伪实时结论 |
| 调整建议生成失败 | 保持原计划不变，并允许再次提交 |

## 8. 三类交付物的一致性

### 8.1 低保真文档

使用线框图覆盖规划输入、规划结果、每日详情、补给图层、动态调整抽屉、调整影响预览和保存状态，并标注关键交互。

### 8.2 Figma 高低保真副本

在一个新 Figma 文件中分别建立低保真和高保真页面区，使用相同页面命名、字段和主流程。高保真页面增加可点击的主流程连线。

### 8.3 代码 Demo V2

复制现有 Demo 到 `demo-v2/` 后增量修改。至少支持生成计划、强度切换、图层筛选、每日卡片联动、途中状态输入、调整影响预览、确认或取消调整、保存提示和重置。

## 9. 验收标准

1. 所有 V2 交付物均为新文件或新 Figma 副本，原模型未被覆盖。
2. 低保真、Figma 和 Demo 使用一致的页面名称、示例路线、字段和状态文案。
3. AI 推荐结果包含可理解的推荐理由，而不只是结论。
4. 补给空窗同时出现在地图和决策信息中，并给出可执行建议。
5. 动态调整必须经过“输入状态—生成建议—预览影响—用户确认”四步。
6. 用户取消调整或调整失败时，原计划保持不变。
7. Demo 在桌面三栏布局下可用，并在窄屏下按规划、地图、详情的顺序堆叠。
8. 原 Demo 仍可独立打开和使用。

## 10. 验证方式

- 对低保真与高保真说明做字段和流程逐项核对。
- 检查 Figma 副本名称、页面层级、页面连线和原文件保留情况。
- 在 Demo 中人工执行生成、筛选、选日、调整、确认、取消、保存和重置流程。
- 检查桌面与窄屏布局，确认无溢出、遮挡或不可操作控件。
- 对比 Git 状态，确认原有模型文件未发生修改。
